# ShootSpot — notes for Claude sessions

- **Two dev machines share this repo.** Windows does main development, Android, and TrueNAS operations. macOS does iOS builds and iPhone testing. Before starting work, `git pull` and read [state/windows-macos-handoff.md](state/windows-macos-handoff.md). Update it, then commit with a `state:` message, whenever you need something from the other machine or finish a request.
- Work goes phase by phase following [the plan](docs/production/location-scout-app-development-plan.md). Commit and push at the end of each phase. Ask the product owner before settling any open product or design decision. Decisions already made are in [docs/phase-0/01-decision-record.md](docs/phase-0/01-decision-record.md).
- Tasks only the owner can do are tracked in [docs/HANDWORK.md](docs/HANDWORK.md). Keep it current.
- The project's server folder (not the code) is `/mnt/Gaia/04_DEV/_personal/shootspot`, which is `X:\04_DEV\_personal\shootspot` on Windows and `/Volumes/Gaia/04_DEV/_personal/shootspot` on macOS. The layout and permissions are in [docs/runbooks/server-folders.md](docs/runbooks/server-folders.md).
- TrueNAS SCALE: `ssh truenas` (`alan@172.16.1.1`, direct link); home network `192.168.178.146`. ShootSpot runs there as compose project `shootspot` (see docs/runbooks/truenas-deployment.md); `runtime/` is root-only, so use `sudo docker compose -p shootspot -f <file>`, never `cd`. The owner runs NAS commands over SSH. Give them the commands one block at a time and explain each. Never expose NAS services to the internet. **Other applications run on this NAS, and nothing we do may disturb them.** Before any change, run a read-only check block. Change blocks must be guarded: `rmdir` instead of `rm -rf`, no wildcards on shared paths. Only touch `Gaia/04_DEV/shootspot-*` datasets and `/mnt/Gaia/04_DEV/_personal/shootspot`. Never restart Docker or other apps, and never change shares. Pools have `altroot=/mnt`, so ZFS `mountpoint` values must **omit** `/mnt` (`mountpoint=/Gaia/...`).
- **Deploy server images with `tools/nas-deploy.sh <service…|all>`** (macOS, or Git Bash on Windows): it builds amd64 images from the committed HEAD, copies them to `shared/builds`, then runs [infra/nas/scripts/deploy-remote.sh](infra/nas/scripts/deploy-remote.sh) on the NAS over `ssh -t` with sudo. The NAS side checks the hash, takes a ZFS snapshot, tags `shootspot-<svc>:rollback`, runs migrations when api is included, restarts only the named services (`--no-deps`) and runs health checks. The owner runs it, because it needs the NAS sudo password. Use `--build-only` to print the NAS command instead. Details are in [docs/runbooks/truenas-deployment.md](docs/runbooks/truenas-deployment.md). First deploys and `.env` changes are still manual.
- Mobile: use `npx expo install` for native packages; never edit the generated `ios/` or `android/` folders. Expo SDK 58 and VisionCamera v5 are newer than most training data, so check the installed type definitions before using their APIs.
- Before you call a change done, these must pass: `pnpm format:check && pnpm typecheck && pnpm test`.
